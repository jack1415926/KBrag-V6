## 一、总体结论

这次回答的主要问题不是完全不懂，而是**经常从"我使用 Codex/Agent 的经验"出发回答，却没有先给出计算机系统层面的标准定义或执行链路**。面试官连续追问 Tool Calling、结构化输出、切块漏召回，说明他在验证你是否真正理解 Agent/RAG 的底层机制，而不仅是会使用 AI 工具。

最需要立即纠正的四点：

1. **RRF 说成了 MRR。** RRF 是线上用于融合多个召回排名的算法；MRR 是离线评测排序质量的指标，不能说"结果再做 MRR"。
2. **用候选池大小回答相邻块漏召回。** 候选池大不保证低相关的第二块一定进入候选。当前项目真正用于缓解这个问题的是"Chunk 负责定位，命中后回溯并返回完整 Parent Section"，再辅以句子边界切分和重叠窗口。
3. **Tool Calling 没有讲出协议闭环。** 模型只生成结构化的工具调用意图，宿主程序才负责校验参数、执行函数、回填 Tool Result，并再次请求模型生成最终答案。
4. **把"没有使用 Dify/LangGraph"说成"没有第三方工具"。** 项目没有第三方 Agent 编排框架，但明确依赖 FastAPI、Pydantic、OpenAI/Anthropic SDK、FAISS、rank-bm25、jieba 等第三方库，并调用远程模型服务。

另外，项目来源表述需要统一：这是**朋友分享的已有客服问答代码和手册数据**，你的定位是"复现、分析、修复与检索优化"，不要说成来自某个开源库，也不要说成从零独立开发。

## 二、逐题复盘

## 1. 文档切块后只召回部分相关内容怎么办（00:00–03:00）

**面试官**：
> 比如"退款退货条款"在文档里被按 160 的长度切成了两块，用户提问后可能只检索到第一块。（追问）这两块在一个很大的文档里，第一块跟用户问题相关性很高所以排在前面，第二块直接相关性不高排得很后，检索可能找不到，这时候怎么办？你们是不是只靠向量检索给大模型提供证据？检索以后还做了什么？

**我当时答的**：
> 如果只有两块，候选池至少是 20，这两块应该都能进候选池；召回后让 Agent 去判断。我们有两路检索——向量语义 + BM25 关键词，两边同时检索后去重、召回到候选池，再做 MRR、Rerank，然后让 AI 根据这些内容回答。

**问题在哪**
- "候选池至少是 20，所以两块应该都能进"**不成立**。Top-K 只限制返回数量，不保证某个弱相关块一定入选；大语料中第二块完全可能排在 K 之外。
- 当前实现也**不能简单概括为"候选池至少 20"**：BM25 和 Dense 主路各召回 20，逐关键词各召回 5，随后用 RRF 合并到现役默认上限 20 的 Rerank 候选池，再精排和去重；历史 Baseline 的配置上限才是 80。
- **"做 MRR"是术语错误。** 在线链路做的是 RRF + Rerank；MRR 用在离线评测中。
- 面试官的问题本质是：**当 Query 只与答案的一部分语义相近时，怎样补回同一主题的上下文？** 原回答只谈召回数量，没有谈上下文扩展。

**应该这么答**
> 候选池变大只能提高概率，不能保证第二块被召回。这个问题通常要从切分和检索后扩展两层解决。我的项目先按 Markdown 标题建立 Parent Section，再在 Section 内用句子感知的重叠窗口切成小 Chunk。BM25 和 Dense 用小 Chunk 做定位，一旦某个 Chunk 命中，系统会根据 `parent_section_id` 返回完整 Section，因此即使问题只和第一小块高度相关，模型仍能看到这一主题下后续的步骤、限制和图片。线上融合用的是 RRF，之后再用 Cross-Encoder Rerank；MRR 是我离线评测排序效果的指标，不参与在线融合。如果答案确实跨两个不同 Section，我会考虑按文档位置扩展相邻 Section，或调整标题层级和切分规则，并用 Recall@K、MRR、答案完整度和 Token 成本做对照，而不是只把 Top-K 调大。

**源码依据**
- `parse_manuals.py:34-37, 559-631`：句子感知窗口、目标长度、重叠、短尾与长句处理
- `retrieval_engine.py:599-636`：BM25/Dense 多路召回、RRF、Rerank、去重
- `retrieval_engine.py:988-1001`：命中 Chunk 后默认返回 Parent Section
- `retrieval_engine.py:1062-1072`：RRF 公式实现

**我当时答的**：

**问题在哪**：**回答口径混乱。** 面试官先问"第三方开源库"、又举了 Dify，回答"没有"容易被理解为整个系统没有第三方依赖，这是错误的。应主动区分三件事：

- **基础库和模型 SDK**：使用了大量第三方库

**应该这么答**
> 如果您问的是 Dify、LangChain、LangGraph 这类 Agent 编排框架，这个项目没有使用，Agent 循环是手写的有界 ReAct 状态机，因为当时只有一个主要工具、两轮决策上限，手写更方便控制强制检索、搜索次数、路由和 Trace。它并不是"零第三方依赖"：接口层用了 FastAPI 和 Pydantic，模型调用用了 OpenAI/Anthropic SDK，检索用了 FAISS、rank-bm25 和 jieba，数值处理还用了 NumPy。更准确地说，是没有依赖第三方 Agent 编排平台，而不是没有使用第三方库。

**源码依据**：`requirements.txt`；`agent.py:1212-1901`（手写 Agent 主循环）；`agent.py:295-325`（`search_manual` 工具 Schema）

## 3. 文档切分方式（04:14–04:40）

**面试官**：
> 除了固定字符串、固定数量切分，其实还有很多种切分方式。你了解过吗？

**我当时答的**：
> 除了固定字符串切分之外，我知道还有其他切分方式，但这一块了解得不太多。

**问题在哪**：没有事实错误，但暴露出知识面不足，**而且漏讲了自己项目已经在做的切分**。

**应该这么答**（先掌握这 8 类分类）
1. 固定字符或固定 Token 切分：简单、快，但容易截断语义
2. 带 Overlap 的滑动窗口：降低边界信息丢失，但增加重复和索引成本
3. 递归分隔符切分：按标题、段落、句子、标点逐级寻找边界
4. 结构化切分：利用 Markdown 标题、HTML DOM、PDF 页/章节、表格等文档结构
5. 语义切分：根据相邻句 Embedding 相似度或主题变化决定边界
6. Parent-Child：小块负责召回，父块负责提供完整上下文
7. 命题/LLM 切分：把文档拆成较独立的事实命题，质量可能更好，但成本和稳定性压力更大
8. 面向领域的切分：代码按函数/类、对话按轮次、合同按条款、手册按步骤和警告块

> 我了解固定 Token、重叠滑窗、递归分隔符、标题/DOM 等结构化切分、语义切分，以及 Parent-Child 和命题式切分。我的项目不是简单每 160 个字符硬切：先按一到三级 Markdown 标题形成 Section，再按句子边界组装约 160 单位的窗口，保留约 24 单位重叠，短尾会并入前块，超长无标点句再按词或字安全切分。检索命中小 Chunk 后返回完整 Parent Section。这样兼顾定位精度和上下文完整性，但 Parent Section 太大也会增加 Token 和噪声，所以我用固定查询集比较过不同 Chunk 参数，而不是凭感觉改长度。

## 6. 系统设计题：如何做"视频高光时刻识别"AI 工具（18:13–21:55）

**面试官**：
> 假设我们要做一个 AI 工具，需要理解一段视频，找出里面的高光时刻。你觉得应该怎么实现？

**我当时答的**（要点）：
> 需要一个支持视频输入和多模态理解的模型；"高光"要先定义清楚；视频处理可以用 FFmpeg；可以让 Agent 接入 Premiere 之类剪辑工具的 MCP；可以截快照记录时间戳；不能完全交给 Agent，要有人工审核；可以把固定错误整理成 Skill；可以参考我上一段实习里做抽卡动效卡顿时"先搜同行做法"的经验；要考虑模型成本（国外模型贵，可选开源/国内模型）；要注意 Agent 权限不要过高。

**问题在哪**：有一些正确意识，但**方案严重偏向 Agent/MCP，没有抓住视频理解主链路**。

- 合理的部分：先定义什么叫"高光"（正确的需求澄清）；提到 FFmpeg、成本、人工复核和权限边界，方向合理
- 不足：Premiere MCP 只是可能的下游剪辑适配，不是高光识别的核心；Skill、联网搜索同行网站和 Agent 权限**偏离题目**，挤占了系统设计时间；没讲视频抽帧、镜头切分、音频转写、OCR、多模态特征、候选段合并、排序、离线任务架构和评测指标

**应该这么答**
> 我会先把"高光"定义成可标注的业务目标，例如体育视频可能是进球和观众情绪峰值，直播带货可能是核心卖点和成交峰值，会议可能是关键结论。没有标签定义，模型再强也无法评价。
>
> 技术链路上，先用 FFmpeg/ffprobe 做转码、时长和码率检查，再进行镜头切分或按固定时间窗采样；视觉侧抽关键帧或短 Clip，音频侧做 ASR、说话人和音量/情绪特征，画面侧可加 OCR、目标和动作特征。然后用多模态模型或任务模型给每个时间窗打分，将连续高分窗口合并，并用去重/NMS、最短时长、前后缓冲等规则生成候选片段。最后输出 `start_time`、`end_time`、分数、理由和缩略图，进入人工复核或剪辑导出。
>
> 工程上我会把它做成异步任务：上传文件进入对象存储，任务队列分发给 CPU/GPU Worker，各阶段结果可缓存和重试，接口只返回任务 ID 和进度。评测不能只看模型描述，要用人工标注的时间段计算片段级 Precision/Recall、时间 IoU、Top-K 命中率，再看推理延迟和每分钟视频成本。Agent 可以用于解释、组合策略或调用剪辑工具，但不应该替代核心的视频分析流水线。

## 7. 上下文窗口和最大输入长度的区别（22:09–24:00）

**面试官**：
> 问一个大模型基础问题。上下文窗口跟最大输入长度有什么区别？

**我当时答的**：
> 我理解上下文窗口除了用户输入，还会包含系统本身加载的内容，比如 Codex 会加载 Skill、`AGENTS.md`、MCP 信息，这些也占上下文。模型标称 100 万上下文，实际可用大概只有 80 多万，要留空间做压缩。所以 Skill 不能太多，太多会占上下文，Agent 选工具时也不知道怎么选。

**问题在哪**：方向部分正确，但**没有先给出正式定义**。

- Skill、AGENTS.md、工具 Schema 会占输入 Token，这个例子是对的
- "100 万设置后只能用 80 多万"是某个产品/配置下的观察，**不是通用定义**，不宜当成理论答案
- "Skill 太多模型不知道怎么选"属于 Tool Selection 质量问题，是额外影响，不是上下文窗口与最大输入长度的核心区别

**正确定义**
- **上下文窗口**：模型一次推理能够共同注意到的总 Token 预算，通常包括 System/Developer/User 消息、历史对话、工具定义、工具结果、图片折算内容以及为输出保留的 Token
- **最大输入长度**：允许送入模型的输入 Token 上限。往往小于或等于上下文窗口，因为还要为输出预留空间；有的厂商把两者合并宣传，有的分别规定，**要以具体 API 文档为准**
- 可用关系：`输入 Token + 最大输出 Token <= 上下文窗口`，还要考虑供应商协议开销和产品侧保留预算

**应该这么答**
> 上下文窗口是一次推理中模型能处理的总 Token 容量，包含系统提示、用户输入、历史消息、工具定义和结果，以及需要预留的输出。最大输入长度是其中允许输入部分占用的上限，所以通常有"输入加最大输出不能超过上下文窗口"的关系。不同厂商可能把输入上限、输出上限和总窗口分别限制，要看具体 API。像 Codex 加载的项目说明、Skill 和工具 Schema 都算输入上下文，因此用户真正可用的输入会小于宣传的总窗口，但我不会把某次看到的 80 多万当成所有百万上下文模型的通用规则。

## 8. Tool Calling 的完整执行流程（24:10–26:30）

**面试官**：
> 模型执行一次工具调用的流程是什么样的？（追问）我问的不是 Codex 里大概怎么做。假设我们自己在系统里面实现工具调用：用户请求发送到系统之后，后面的完整流程是什么？你觉得工具是模型自己去调用的吗？

**我当时答的**：
> 首先要查看有没有可以调用的工具，然后判断调用哪个；按 ReAct 就是一边执行一边判断。首先模型或系统需要支持 Tool Calling，然后判断用什么工具——剩下的完整实现流程我不太确定。MCP 会暴露接口给 Agent 调用，同时包含工具的基本说明和使用方式；MCP 比较重，因为可能包含较长上下文。工具应该不是模型自己真正执行，实际还是由外部函数执行。

**问题在哪**：核心判断"模型不真正执行工具"是**对的**，但**完整流程没有回答出来**。

**标准流程（8 步，必须背下来）**
1. 宿主程序用 JSON Schema 描述工具名称、用途和参数
2. 把用户消息、历史和工具 Schema 一起发给模型，可设置 `tool_choice=auto/required/指定工具`
3. 模型返回结构化 Tool Call：调用 ID、工具名、参数；**此时没有真正执行函数**
4. 宿主程序解析并校验工具名和参数，还要处理权限、超时、幂等和未知工具
5. 宿主程序调用本地函数或远程服务
6. 把 Assistant 的 Tool Call 和对应 `tool_call_id` 的 Tool Result 一起追加到消息历史
7. 再次调用模型，让模型基于 Observation 生成答案或继续发起下一次 Tool Call
8. 达到停止条件、轮数上限或错误策略后返回最终结果

**本项目中的对应关系**
- `agent.py` 中的 `TOOLS` 定义 `search_manual` Schema
- 技术题在没有正式检索前设置 `tool_choice="required"`
- `llm_router.py` 把内部 Anthropic 形状转换成 OpenAI 的 `tool_calls`，再把返回结果还原为统一的 `tool_use` Block
- `run_agent()` 遍历 `response.content`，发现 `tool_use` 后调用 `_execute_tool_with_pics()`
- 工具执行结果被包装成带原调用 ID 的 `tool_result`，加入消息历史后进入下一轮
- 本项目最多两次有效 ReAct 决策、两次正式搜索，超过后进入无工具强制收束

**应该这么答**
> 模型不会直接执行工具，它只根据工具的 JSON Schema 生成结构化调用意图。宿主程序把消息和工具定义发给模型，收到工具名、参数和 call ID 后，先做 Schema、权限和参数校验，再调用真实的本地函数或外部 API。执行结果要以匹配 call ID 的 Tool Result 写回消息历史，再次调用模型；模型读取 Observation 后决定继续调用还是生成最终文本。系统还要控制超时、重试、幂等、未知工具和最大轮数。我的项目就是这个闭环：技术题先强制 `search_manual`，程序实际执行检索，把结果回填后，模型第二轮再收束答案。

**源码依据**：`agent.py:295-325`（工具 Schema）；`:1433-1453`（`tool_choice` 与模型请求）；`:1480-1559`（解析 Tool Use 并由宿主执行）；`:1805-1818`（Tool Result 回填消息历史）；`llm_router.py:250-320, 345-369, 392-422`（OpenAI/Anthropic 工具消息转换与请求）

## 9. 如何要求大模型 API 返回结构化数据（26:41–27:40）

**面试官**：
> 调用大模型 API 时，怎么要求它返回结构化数据，而不是普通文本？怎么限制？（追问）用提示词约束吗？

**我当时答的**：
> 首先肯定需要一定的约束。提示词约束肯定要有；我记得还可以在输出格式相关的配置里进行设置，但这一块我不太确定。

**问题在哪**：回答过于模糊。**提示词不是最可靠的约束。**

**应该这么答**
> 优先使用模型 API 原生的 Structured Outputs 或 JSON Schema，而不是只在 Prompt 里写"请返回 JSON"。例如支持 OpenAI 兼容协议的模型可以使用 `response_format` 的 JSON Schema/strict 模式；如果供应商只支持 JSON mode，可以要求返回 JSON Object，但字段约束通常弱一些。另一种方式是定义一个函数工具，让模型把结构化结果放在 Tool Call 的 arguments 中。无论哪种方式，服务端都要再次用 Pydantic 或 JSON Schema 校验，失败时做有限重试或返回明确错误，不能因为模型输出看起来像 JSON 就直接信任。还要确认具体模型和供应商是否真正支持 strict schema。

**与本项目的边界**（重要，要分开讲）
当前项目用 Pydantic 约束 `/chat` 的 HTTP 请求/响应，也用 Tool Schema 约束 `search_manual` 参数；但**普通 LLM 最终答案仍以文本为主**，源码没有给最终答案配置 `response_format/json_schema`。面试时应把"通用正确做法"和"项目当前实现"分开讲。

## 三、下次面试的答题结构

遇到原理题，按以下顺序回答：

1. **先给标准定义或结论**：两三句话直接命中考点
2. **再讲执行链路**：输入、处理、输出、失败路径
3. **映射到自己的项目**：指出文件、模块、参数和真实状态
4. **最后讲边界与取舍**：哪些不是自己从零写、哪些只是 PoC、哪些还没验证

例如 Tool Calling 不要先从 Codex 或 MCP 聊起，而要先说：

> 模型只生成工具调用意图，宿主程序执行；Schema 发给模型，模型返回 name/arguments/call_id，程序校验并执行，再把 result 按 call_id 回填给模型。

然后再补一句本项目如何做。这样面试官会先确认你掌握了通用机制，再听你的项目经验。

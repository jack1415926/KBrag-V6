## 0. 读前须知：Python 机制 ↔ C++ 对照

这份文档里有几处 Python 特有机制，用 C++ 打比方能秒懂：

| 本文出现的 Python 概念 | C++ 里对应什么 | 关键差异 |
|---|---|---|
| `@contextmanager` + `try/finally`（`request_scope`） | **RAII**：构造时 set，析构时 reset | 完全同构。`with` 块退出 = 析构，异常也会走 `finally` = 析构不会漏 |
| `ContextVar` | **`thread_local` 的反面** | `thread_local` 绑线程 → 线程池复用时数据串；`ContextVar` 绑"这一次逻辑执行"，跨线程时**显式拷贝一份** |
| `threading.Event` + 检查点 | **C++20 `std::stop_token` / `std::jthread`** | 一模一样的设计哲学。`std::jthread` 析构自动 `request_stop()`；这里 `cancel_event.set()` 就是 `request_stop()`，`check_cancelled()` 就是 `stop_requested()` |
| `remaining_timeout()` | `std::chrono::steady_clock::time_point deadline` + 每次算子操作时间 | 同一种"总预算下传"的写法 |
| `os.environ[...] = x` | `setenv()` / `putenv()`（**进程级全局**） | 并发请求会互相覆盖，和 C++ 全局变量一个毛病 |
| 无编译期 | C++ 有 **`-Wunused-function`** 等编译警告 | **Python 没有编译器**，所以"写好了但没人调用"的死代码不会有任何提示 —— 这是本次发现的最重要 bug 的成因 |
| `asyncio.to_thread()` | 把阻塞任务 `post` 到线程池，避免卡住 event loop | 和 asio 的 `io_context` + thread_pool 思路一致 |
| `unittest` | gtest | 断言风格类似，`python -m unittest discover` = `ctest` |
| `dict.fromkeys(list)` | `std::set` 但有**插入序**（C++ 里得 vector+set 配合） | — |
| `@dataclass` | `struct` + 自动生成的构造/比较/打印 | — |
| `assert` 自检（`__main__` 块） | 运行时版的 `static_assert` / 迷你单测 | 跑 `python 文件.py` 就会执行 |

## 3. 检索 / RAG 层

### 3.1 RRF 从"死代码"变成"主路径"

**RRF 是什么**：合并多份排名时，不能直接加分数（BM25 无上界、余弦 0~1，量纲不同）。
RRF 只看**名次**：`得分 = Σ 1/(60 + 名次)`。在两份名单里都排第 1 → `2/61` → 自动浮到最前。

**旧版实情**：
```bash
grep -n "_rrf_merge" 旧版/retrieval_engine.py
# 686:    def _rrf_merge(...)      ← 只有定义，零调用点（死代码）
```
`_rrf_merge()` 函数写完整了、有中文 docstring 解释原理，**但从来没有任何代码调用它**。

主检索路径实际是拼接截断：
```python
candidates = list(dict.fromkeys(
    sparse_doc_ids + dense_doc_ids + extra_sparse_doc_ids + extra_dense_doc_ids
))[:80]
```

三个后果：
1. **顺序即偏见**：拼接后 1–20 位全是 BM25 的、21–40 位全是向量的。"向量排第 1、BM25 排第 30"的文档只能排到第 21 位，强信号被淹没。
2. **截断丢掉最后一份名单**：四份名单长度是 `20 + 20 + N×5 + N×5`（N=关键词数）。9 个关键词时 130 个 → 截到 80 → `extra_dense`（逐关键词向量扩展召回）**整份被切掉**。
3. **被切掉的恰好是最值钱的**：逐关键词召回是拿"DCB107"这类**型号词**单独搜的，而型号词正是整句搜索最容易漏的。

**新版**：
```python
ranked_lists = self._collect_text_recall_rankings(...)   # 四份名单各自独立保留
candidates = self._rrf_merge(ranked_lists, top_n=self.rerank_candidate_pool)
```

> **⚠️ 诚实边界（面试必须主动说）**
> 在这批 30 题金标上候选数**最多 34 个**（中位 27.5），**从未触碰 80 的上限**，
> 所以**没有 "RRF vs 拼接" 的 A/B 数据**。
> 准确表述：**「正确性修复 + 使能改动」**——消除了一个关键词多时静默丢召回的缺陷，
> 同时让候选池消融实验成为可能。**不要说成"RRF 带来了提升"**。

### 3.2 视觉四路检索（全新子系统，最大架构增量）

**解决什么问题**：用户传一张照片问"这个按钮在哪"——问题里没有产品名、没有部件名，纯文本检索无从下手。

```
建库：2,605 张插图 → 过滤 → 2,504 张 × 4,096 维 IndexFlatIP（41 MB）
      过滤规则：caption.category != "noise"（排除 59 张）+ 必须被某 section 引用（排除 42 张孤儿图）
      每张图元数据：image_id / product / section_keys / caption / sha256
      硬断言：if len(items) != 2504: raise    ← 防止静默漂移
      模型：Qwen/Qwen3-VL-Embedding-8B（SiliconFlow 端点）

查询：四路并行
  路1  原始问题          → 文本检索     ← 关键，见下
  路2  Vision 扩展文本    → 文本检索
  路3  扩展文本          → 视觉索引（文查图）
  路4  用户上传图        → 视觉索引（图查图）
        ↓ Section 粒度 RRF（k=60），key = "产品|parent_section_id"
        ↓ 多模态 VL Rerank（Qwen/Qwen3-VL-Reranker-8B）
        ↓ 多图分别 rerank 结果再 RRF 一次
```

**两个设计要点**：

1. **路1（原始文本锚定）是实验逼出来的**。第一版只有路2/3/4，四组对照实验直接 FAILED（Section R@5 从 65.00% 反降到 63.33%）——归因到**融合时丢掉了原始问题自己的排名**：路2 用的是 Vision 改写文本，改写有噪声，而原问题的检索结果没进 RRF 池。加上路1 后质量才达标。
2. **VL Rerank 的 Query 是图文对对象** `{"text": query, "image": 用户图}`，Document 是 `{"text": 产品+标题+摘要+正文, "image": 命中图}`。多张用户图**分别 rerank 再 RRF 融合**，因为 VL Reranker 对单图更稳。

### 3.4 分词器 `tokenize_mixed_clean()`

**实测对比**（输入 `"扶手<PIC> 使用扶手 USB-C 充电"`）：

```
旧版: ['扶手','扶手','pic','使用','使用','扶手','扶手','usb','-','c','充电','充电','使用扶手','usb-c']  ← 14 个
新版: ['扶手','使用','扶手','usb-c','充电']                                                        ← 5 个
```

旧版三个毛病：
1. **`<PIC>` 标记被切成词** `'pic'`——所有 chunk 都有这个标记，成了高频无意义词，稀释 BM25 区分度。
2. **两字中文词被重复计算**：双字片段补充代码 `for i in range(len(word)-1): tokens.append(word[i:i+2])`
   对两字词会追加**和原词完全相同**的片段。实测 `扶手` 在原文出现 2 次却输出 4 个，
   **每个两字词的 tf 凭空翻倍**，直接扭曲 BM25 的 tf 项。
3. **型号词被切碎**：`USB-C` → `usb` / `-` / `c`。

新版修法：
```python
text = _STRUCTURE_MARKER_RE.sub(" ", text)                     # ① 抹掉 <PIC>/[[PIC:xxx]]
for word, start, end in jieba.tokenize(text, mode="search"):   # ② 带位置的分词
    candidates = [(start, end, word)] + [(start+i, start+i+2, word[i:i+2]) for i in ...]
    for item in candidates:
        if item not in seen_positions:                         # ③ 用 (起,止,词) 三元组去重
            positioned.append(item)
for match in _ASCII_TOKEN_RE.finditer(text):                   # ④ 型号正则整体保留
    positioned.append(...)
positioned.sort(key=lambda x: (x[0], x[1]))                    # ⑤ 按原文位置排序
```

③ 是关键：对 `"扶手"`，双字片段 `(0,2,"扶手")` 和原词 `(0,2,"扶手")` 是**同一个三元组** → 去重 → 只计一次。实测新版正好输出 2 个 `扶手`（等于原文出现次数）。

> **⚠️ 诚实状态**：**这个函数没有接进运行时**。运行时 3 处仍调用旧的 `tokenize_mixed`；
> 新函数只在 `__main__` 自检里被跑过。doc 06 里 T0/T1 对照表**整张是"待实验"**。
> 要说就说：**"实现了并有自检断言，但还没重建索引做 A/B"**。

## 4. 运行时链路层

### 4.1 请求级状态：从两条"暗渠"到 `contextvars`

**背景**：FastAPI 是异步单线程事件循环，但 Agent 是同步阻塞代码，所以用 `asyncio.to_thread()`
扔进**线程池**执行。**线程池的线程是复用的**（同 C++ thread pool）。

**旧版怎么传 qid**：
```python
os.environ["CURRENT_QID"] = str(question_id)                # 暗渠① 进程级全局
_retrieval_engine._RERANK_CONTEXT.qid = str(question_id)    # 暗渠② thread_local
```

为什么叫"暗渠"（side channel）：**不走显式参数，偷偷写进全局/线程上下文，让下游自己去读。**

三个坏处：
1. **`os.environ` 全进程共享**：请求 A 设 "64"，请求 B 设 "0" → A 的日志记成 0。**并发互相污染。**
2. **`thread_local` 线程复用导致脏读**：A 用完线程没清理，B 拿到同一线程读到 A 的 qid。**泄漏。**
3. **读取处把两条暗渠串起来**：`getattr(ctx,"qid",None) or os.getenv("CURRENT_QID")`
   —— 取不到就退回进程全局，出问题根本不知道读的是谁的值。

**新版**（`request_context.py`）：
```python
_QID / _DEADLINE / _CANCEL_EVENT = ContextVar(...)          # 每请求一份

@contextmanager
def request_scope(*, qid, deadline, cancel_event):
    tokens = [_QID.set(qid), _DEADLINE.set(deadline), _CANCEL_EVENT.set(cancel_event)]
    try:
        yield
    finally:
        for var, token in reversed(tokens):    # 逆序恢复，像栈
            var.reset(token)
```

`ContextVar` 是 Python 3.7+ 标准库机制："逻辑执行上下文"里的变量——**不是全局、不是线程绑**。

关键语义：**`asyncio.to_thread()` 会把当前 context 复制一份带进工作线程**，所以：
- 请求 A 的线程里 set 的值，B 看不到（**隔离**）
- 线程复用时 context 是本次任务新复制的，**不残留上次的值**（无脏读）
- `finally` + `reset(token)` 保证异常也不会漏（**等同 RAII**）

若 Agent 内部再开线程池，必须**显式继承**：
```python
pool.submit(copy_context().run, analyze_query_images, ...)
```
新开线程不会自动拿到 context —— **这是面试官最容易追问的点**。

### 4.2 超时预算裁剪 + 协作取消

**旧版的数学问题**：一次请求里下游调用是**串行**的：
```
Embedding 30s → Rerank 30s → LLM 30s = 最坏 90s   （但请求总预算只有 50s）
```
旧版每个调用各拿一个**完整**超时：`timeout=self.timeout`（永远 30，不管请求跑了多久）。

后果：请求跑到 50s 被 `asyncio.wait_for` 掐掉返回 504，**但线程里那个 HTTP 请求还在跑**
（Python 杀不掉阻塞中的线程，就像 C++ 不能安全强杀线程一样）。
它继续烧 token、占并发额度直到自己的 30s 结束 —— **用户早收到错误了，钱还在花**。

**新版**：
```python
def remaining_timeout(default):
    remaining = _DEADLINE.get() - time.monotonic()
    return max(0.001, min(default, remaining))
```
每次调用拿 `min(自己的超时值, 请求剩余时间)`：
```
请求开始 剩50s → Embedding = min(30,50) = 30s
跑到40s  剩10s → Rerank    = min(30,10) = 10s
跑到48s  剩 2s → LLM       = min(30, 2) =  2s
```
**预算像漏斗一样往下传**，"请求总耗时 ≤ 总预算"这个不变量成立。

**协作取消（cooperative cancellation）**——和 C++20 `std::stop_token` 同一套哲学：
> **不是我过去把门掰开，而是按下"开门"按钮亮灯，电梯在下一个安全楼层自己停。**

```python
cancel_event = threading.Event()          # == std::stop_source
# 超时 / 客户端断连时：
cancel_event.set()                        # == request_stop()

def check_cancelled():                    # == stop_requested()
    if cancel_event.is_set() or time.monotonic() >= deadline:
        raise RequestCancelled
```

检查点位置：Agent 主循环**每轮**、LLM **流式每个 chunk**（最值钱）、rerank/embedding **发起前**、
并发信号量 `acquire(timeout=...)`。

**关键配套**：`RequestCancelled` 一路上抛时会被各层 `except Exception` 兜底吃掉，变成假正常结果。
必须显式放行：
```python
except RequestCancelled:
    raise                                  # ← 先放行，别被兜底吃掉
except Exception as exc:
    print(f"降级回退: {exc}")               # 其他错误才降级
```
这就是 `llm_router` / `rerank_client` / `retrieval_engine` 里到处都有这一对 `except` 的原因。

**`_BACKGROUND_AGENT_TASKS`**：超时后 `wait_for` 不等了，但 task 还在跑（用了 `asyncio.shield()`
保护它以保留句柄）。不处理的话它结束时的异常无人接收 → Python 警告
`Task exception was never retrieved`。所以超时后塞进集合 + 挂回调消费掉。
`/health` 新增字段 `background_agents` = **当前还有几个僵尸 worker 在收尾**（可观测性）。

## 5. 修复的 Bug 清单（含定位方法）

> **这一节是简历上最抗追问的内容**——它证明逐行读懂了别人 8000 行代码。
> 重点不是"我修了什么"，而是"**我是怎么发现的**"。

### 5.1 RRF 死代码 → 接入主链路 【静默】

- **表现**：无报错、无日志、结果看着正常，只是质量次优；关键词多时静默丢一整份召回名单
- **怎么发现的**：`grep` 函数名，发现**只有定义行、零调用点**
- **C++ 视角**：C++ 里 `-Wunused-function` 会直接警告，**Python 没有编译期所以零提示**
- **修法**：四份名单各自保留 → `_rrf_merge(ranked_lists, top_n=pool)`
- **⚠️ 无 A/B 数据**（见 3.1）

### 5.2 `default_products` 传了但没生效 【静默】

一行之差：
```python
products = input_data.get("products") if has_products_key else None            # 旧
products = input_data.get("products") if has_products_key else default_products  # 新
```

- **为什么有人这样写**：设计意图是"模型没填 products 就自动套产品路由结果"。`default_products` 参数
  **一直存在**，调用点老老实实传了 `current_route.products or None`，debug 日志里打了它，
  trace 里也序列化了它（`"default_products": [...]`）—— **唯独检索时没用**。
- **具体后果**：用户问"这个相机怎么装三脚架" → 路由正确输出 `["Camera"]` → 模型调工具时只填了
  `keywords`（`products` 本就是选填）→ 旧版 `products = None` → **在全部 39 本手册里搜** → 可能命中
  "电钻手册"里带"安装"的段落 → **串产品**。产品路由白算了。
- **为什么静默**：`DEBUG_ROUTE=1` 下日志是
  `[TOOL] search_manual llm_products=<unset> default=['Camera'] → used=None` —— **值就明晃晃在日志里**，
  但看着像正常调试输出。trace 里 `default_products` 也是对的，**所有可观测点都显示正确，唯独行为错**。
- **新版保留的细节**：`has_products_key` 判断依然必要——模型若**显式**传 `products: []`（表示全库搜），
  新版尊重空列表**不**回退到默认产品。区分"没传"和"传了空"。

### 5.3 后处理 `question_text` 越界引用 【不静默，但触发条件罕见】

旧 `agent.py:801`，在 `_postprocess_final_answer` 内部：
```python
def _postprocess_final_answer(*, answer, question, ...):    # 形参叫 question
    ...
    answer = _rewrite_single_product_answer(
        question=question_text,      # ← 这个名字只是 run_agent 的局部变量
    )
```
- **触发条件**：`route_products` 非空 + 非对比类问题 + 答案同时出现 ≥2 个路由产品
- **为什么从未崩过**：路由通常只产出 1 个产品，`len(mentioned) >= 2` 达不到 → 实际不可达
- **修法**：`question=question`
- **⚠️ 措辞**：说"修复一处**潜在** NameError，正常单产品路由下不可达"，**别说"修了线上崩溃"**

### 5.4 `validate_performance.py` 硬编码伪指标 【静默｜⚠️ 旧版就有，非你引入】

- `ROUTER_REPEAT_RESULTS`（第 41 行）是**硬编码的历史常量**：5 次 × 400 题 = 400/400，
  脚本**不会重测**，只把它渲染成表格
- `FINAL_ANSWER_PRODUCT_WRONG_IDS = {"432","433"}` 同为写死，
  那个"最终答案产品 348/350 = 99.43%"就是这么算出来的
- **旧版完全相同**（4 处行号逐字一致）
- **你的改法**：没删掉、没装看不见，在生成的报告里加了一行口径说明：
  > 口径：入口 Service/Tech 五次 400 题结果来自历史常量；产品路由 Top-1/Top-3 由当前 ProductRouter
  > 离线重算；图文指标检查已保存参考答案与当前图片/Caption 资产的一致性，不代表当前模型重新生成 400 题。
- **面试话术**："我核对交付验证报告时发现，其中一组 100% 的指标其实是上游脚本里硬编码的历史常量、
  不是可复现实验。我没有删掉它，而是把数据来源和重算范围标注清楚。"

### 5.5 路由 Prompt 里的产品计数写错

`product_router.py:211` 送给模型的 prompt 里写着「英文产品（20个）」，实际 19 个；
同文件两处 docstring 写「40 本产品手册」，实际随包 39 本。**这个数字是进 prompt 的**，不只是注释。

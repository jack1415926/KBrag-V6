# 验证报告

## 1. 验证目标

本报告记录 KBrag V6 当前版本的可复现证据、历史结果与已知边界，验证目标包括：

1. 代码包完整，可安装依赖并启动 API；
2. 核心端点 `POST /chat` 可接收 JSON 文本和 Base64 图片字段；
3. `/chat` 返回统一 JSON 响应，具备鉴权、校验、超时和错误处理；
4. 产品技术问题可进入手册 RAG 链路，完成产品路由、检索、图文证据注入和答案格式化；
5. 客服问题与技术问题分轨处理，避免互相污染；
6. 静态检查能够发现缺失文件、语法错误、密钥扩散和缓存污染；
7. 历史离线结果与当前 Qwen3 结果明确分开，避免把旧数据写成个人优化成果。

#### 6.4.7 请求并发隔离与协作超时整改（2026-09-08）

整改前，`run_agent()`会把题号写入进程级 `CURRENT_QID`，并同时写入未统一清理的Thread Local；并发请求可能覆盖环境变量或在线程复用时残留题号。当前已改为ContextVar保存请求QID，并由请求作用域在退出时恢复原上下文，Rerank日志不再读取进程环境变量。

整改前，`asyncio.wait_for(asyncio.to_thread(...))`超时只停止等待，无法终止后台Python线程；同时Embedding、Rerank和LLM各自使用独立且更长的超时/重试。当前API为每个请求建立统一单调时钟截止时间和取消事件，LLM、Embedding、Rerank、路由信号量等待与Rerank退避均使用剩余请求预算。API返回504或调用协程被取消时设置取消事件，并通过 `background_agents` 跟踪尚在退出的worker；超时请求不会写入session历史。

Python线程不能被安全强杀，因此若取消发生在socket阻塞内部，线程仍需等待该次网络调用按照下传的剩余超时返回；返回后会在下一检查点终止，不会继续后续Agent轮次。7项标准库回归覆盖双线程QID隔离、截止时间、取消事件、LLM/Embedding/Rerank超时下传，以及 `/chat` 504后worker回收，全部通过。

#### 6.4.11 视觉检索阶段级延迟剖析（2026-09-17）

为区分本地检索成本和远程服务长尾，在原实验脚本中增加可选调用级计时，记录Vision、原始/扩展文本Embedding与Rerank、VL文本/图片Embedding、VL Rerank及底层HTTP时间区间、状态码和负载。首轮240条剖析记录错误0；最慢融合请求中扩展文本Embedding等待72.93秒、原始文本Embedding等待20.11秒，而VL Embedding约1秒、文本Rerank约1.75秒、VL Rerank约0.81秒。

随后两轮结构与并发对照继续记录阶段时间线。三次相同P四路结构的P95分别为16.47、71.57和12.26秒，最大值分别为75.85、102.11和14.58秒；本地代码与检索结构没有变化。汇总360次P调用，扩展文本Embedding最大95.81秒、原始文本Embedding最大98.21秒；文本Rerank最大不足20秒、VL Rerank最大4.59秒。结论是极端长尾主要位于远程文本Embedding HTTP请求，VL Embedding也出现过约120秒后返回500；本地FAISS、RRF和VL Rerank不是极端长尾来源。客户端计时不能继续拆分公网传输、服务端排队和模型计算。

完整记录见 `experiments/visual_latency_20260917_133735/operation_record.md`。

#### 6.4.12 P/M/S替代方案对照（2026-09-17）

P保留原始文本、Vision扩展文本、文本查图和图片查图四路；M合并两条文本的BM25/Dense排名后只执行一次共享文本Rerank；S保持P排序但把文本远程调用限制为单并发。B/P/M/S实验480条中有1次VL图片Embedding等待120.48秒后HTTP 500；P/M/S顺序平衡确认360条中有1次VL文本Embedding等待120.55秒后HTTP 500，其余记录完成，VL Rerank回退0。

顺序平衡确认在共同119条成功样本上：P的Section/Image Recall@5为79.83%/68.07%，中位数5.70秒、P95 12.28秒；M为80.67%/65.55%，中位数8.22秒、P95 18.67秒；S为79.83%/68.07%，中位数8.60秒、P95 36.68秒。M虽然少一次远程Rerank，但把候选和单次负载扩大，两次独立实验均出现Image Recall下降且没有稳定延迟收益；S的尾延迟收益也未复现。因此不以M/S替换P，本轮视觉优化阶段性收束。

完整记录见 `experiments/visual_merge_concurrency_20260917_150134/operation_record.md`与 `experiments/visual_pms_confirm_20260917_173923/operation_record.md`。

#### 6.4.13 在线文本检索远程调用审计（2026-09-22）

源码审计与实际索引回读确认：文本索引为单个 `faiss.IndexFlatIP`，包含6,570条4,096维 `Qwen/Qwen3-Embedding-8B`向量；39份手册不是39个独立向量库。历史正式 `search_manual` 会把主Query与逐关键词Dense分成多次串行HTTP；当前已接入 `TEXT_QUERY_EMBED_MODE=serial|batch`，默认 `batch`，只把正式路径原本已选的动态N条文本合并为一次请求，返回向量后仍分别执行原FAISS/RRF/Rerank。该开关不生成关键词，也不改变Tool Call内容。

Parent Section通过已加载的内存字典逐条回查，不访问数据库、磁盘或远程服务，不是当前优化重点。`EMBEDDING_MAX_CONCURRENCY=4`仍只约束离线建索引；多个 `/chat` worker可以同时访问同一远程账号，但当前实验没有出现429，不能把远程长尾直接归因为限流。文本与VL Embedding/Rerank客户端现按工作线程复用 `requests.Session`，避免跨并发线程共享一个Session。

现有旧Trace显示两次正式 `search_manual` 总耗时分别为9.462秒和30.876秒；后一请求的预检索为Dense 8.561秒、Rerank 0.530秒。2026-09-22已将细粒度检索计时接入Tool事件的 `retrieval_timings`：记录主BM25、主Dense、逐关键词BM25/Dense、RRF、关键词/原始问题Rerank、Parent Section回填和总耗时，Dense调用另记录输入条数、HTTP状态码和错误类型；视觉开启时分别保留扩展文本与原始文本子链路。当前10项Trace/实验、12项API/网页、8项请求上下文和14项视觉测试共44项通过；文本与VL客户端按线程复用HTTP Session。

同日完成5轮固定问题串行基线，5/5成功、错误0，Embedding HTTP状态均为200；完整检索中位8.024秒、最大19.976秒。4次逐关键词Dense合计中位4.188秒、最大13.260秒；最慢轮全部Embedding占总耗时90.9%。RRF与Parent回填均约数十微秒，BM25除首次分词预热外约数十毫秒。

#### 6.4.14 文本多Query发送方式与探索性Query实验（2026-09-22）

固定真实风格的“主Query+4关键词”输入对照显示：串行5请求、批量1请求、并行5请求均成功且最终Parent Section签名一致；批量总耗时中位4.322秒，低于串行10.383秒和并行5.572秒。该结果支持“当正式路径已经决定需要N条同模型Embedding文本时，将相同动态N条输入批量发送”。

为扩大多Query样本，后续30题脚本人为生成确定性关键词；这改变了旧金标原本 `keywords=[]`、完整问题单路的Query构造，又引出了完整问题、关键词主路和混合策略对照。相关产物保留，但统一降级为探索性记录：不替代真实Agent Tool Call，不作为生产Query策略依据，也不把简单关键词造成的24/30归因于批量传输。正式Agent的Tool Schema、`query`和 `keywords`生成逻辑未因此修改。

#### 6.4.15 最新视觉Fusion两轮基线（2026-09-22）

默认批量配置下运行40题Fusion两轮，共80条正式检索，80/80成功、错误0、VL Rerank回退0。Section Recall@5为78.75%，Image Recall@5为68.75%，错误图片率31.25%；完整Fusion中位5.788秒、P95 15.256秒、最大23.46秒。阶段时间线显示长尾来自远程文本Embedding和文本Rerank，VL阶段相对稳定。

该视觉脚本显式使用 `keywords=[]`，原始文本和Vision扩展文本分支各只有1条Qwen3文本Embedding输入；160次文本Embedding HTTP的 `payload_items`均为1。因此本轮是最新视觉绝对基线，不能证明批量降低视觉延迟。Vision分析预先计算且不计入Fusion墙钟；本轮也未运行同轮 `vision_to_text`基线，不能正式判定相对延迟门槛通过。完整产物见 `experiments/visual_batch_fusion_20260922_2rounds/`。

## 11. 验证结论

KBrag V6 当前版本已完成 API、源码、运行数据、检索索引、手册知识库、验证脚本和项目文档整理。现有证据表明：

1. `POST /chat` 可以处理文本与Base64图片请求；
2. 源码包具备可安装、可启动、可自检的复现条件；
3. `validate_performance.py` 可生成验证报告所需数据表，覆盖 RAG 检索、图文一致性、路由准确性和对话连贯性；
4. 2026-09-23静态自检记录的docstring覆盖率为59.9%（260/434）；交付检查仍被两个已有本地文件阻断；
5. 技术链路具备产品路由、混合检索、图文锚点和幻觉抑制机制；
6. 2026-09-02已验证Qwen3索引和DeepSeek文本/视觉Flash端到端链路；固定金标上的Rerank候选池与Chunk参数指标已完成，BM25分词与架构级Chunk策略指标仍待补充。
7. 旧400题数据只作为历史回归材料，不能直接写成当前优化收益。
8. 客服Prompt优化已保留修改前、V1及V2代表性多轮对话；当前结论是部分验证，不是生产效果声明。

动态进度不在本报告维护，以 `项目面试，运行问题说明文档/项目当前进展与下一步.md` 为准。

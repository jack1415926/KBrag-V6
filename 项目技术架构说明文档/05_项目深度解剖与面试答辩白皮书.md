## 0. 阅读口径与结论先行

项目的准确定位是：

> **一个面向中英文产品手册的、双轨路由的多模态客服 Agent。技术分支采用手写 ReAct 状态机驱动单工具 `search_manual`，检索侧使用 BM25、Qwen3-Embedding-8B 向量召回、RRF、Qwen3-Reranker-8B 和 Parent Section 回溯；在线接口由 FastAPI 提供鉴权、会话短历史、超时和 Trace。文本请求使用 DeepSeek V4 Flash，上传图片时切换 DeepSeek V4 Flash Vision Exp。**

需要避免的两个常见误解：

1. 项目**没有使用 LangChain 或 LangGraph**，`requirements.txt` 和源码均无相关依赖/调用；编排逻辑集中在 `agent.py::run_agent()`。
2. RRF负责融合不同召回列表的排名，Cross-Encoder Rerank负责对融合后的候选做Query-Document相关性精排，两者不是同一层。当前 `search_manual()` 已调用 `_rrf_merge()`。

当前数据资产为39份 Markdown 手册（中文20、英文19）、1,943个 Section、6,570个 Retrieval Chunk、2,567条图片 Caption，代码和项目说明已统一该数量口径。

### 1.2 客服分支与技术分支的精确分叉点

在线接口请求没有业务路由ID。真正的业务分叉发生在 `api_server.py::_run_agent_sync()`：

```python
route, classifier_trace = _classify_question(routed_question)
fake_qid = 0 if route == "service" else 64
result = run_agent(..., question_id=fake_qid, ...)
```

`agent.py::run_agent()` 再依据 `question_id` 选择 Prompt：

- `question_id < 64`：`SERVICE_SYSTEM_PROMPT`，不执行产品路由和技术预检索。
- `question_id >= 64`：`TECH_SYSTEM_PROMPT`，执行产品路由、预检索，并要求正式回答前至少调用一次 `search_manual`。

当前实现已在代码层隔离工具：客服分支使用 `active_tools=None`，技术分支才传入 `TOOLS`；因此客服分支不再只依赖Prompt自觉避免检索。

### 1.3 离线题目模式

离线批量运行直接把题目 ID 传给 `run_agent()`：`qid < 64` 硬路由到客服，`qid >= 64` 硬路由到技术。在线 `/chat` 则先分类，再映射为假的0/64，以复用同一套 Prompt 和答案格式化逻辑。

## 2. 硬核技术深潜

### 模块A：Agent 状态机（ReAct）

#### A-Q1：这个 Agent 的 ReAct 循环如何控制轮数？为什么最后一定能收束？

**满分回答：**

主循环在 `agent.py::run_agent()` 中手写实现，核心上限为：

- `MAX_TURNS = 2`：最多两次有效 ReAct 决策机会。
- `MAX_SEARCH_ATTEMPTS = 2`：最多两次正式搜索。
- `MAX_INTERNAL_ITERATIONS = 10`：防止模型反复产生被拦截的工具调用导致内部死循环。

循环条件是：

```python
while effective_turns_used < MAX_TURNS \
        and internal_iterations < MAX_INTERNAL_ITERATIONS:
```

每轮模型可以输出文本或 `tool_use`：

1. 输出 `tool_use`：执行工具，将 Assistant Tool Call、Tool Result 和路由状态提示追加到消息历史；真正执行了工具时，`effective_turns_used += 1`。
2. 输出文本：技术题必须先满足 `formal_retrieval_confirmed`，否则代码拒绝直接回答，追加“先调用 `search_manual`”的状态提示，并消耗一次机会。
3. 搜索次数达到 `MAX_SEARCH_ATTEMPTS`：状态机不再执行工具，返回一段“禁止继续搜索、基于现有证据收束”的伪 Observation，并把本次被拦截的工具调用从统计中减掉。
4. 两轮结束仍未生成文本：调用 `_finalize_without_tools()`，再发起一次不带工具的 LLM 请求，强制根据已有消息和证据生成最终答案。
5. 强制收束仍返回预设异常占位句：抛出 `RuntimeError`，交由 API 层记录 Trace 并返回500，而不是把假成功交给用户。

这不是无限自主规划，而是“有界 ReAct”：用固定上界换可控成本、尾延迟和接口运行稳定性。

#### A-Q2：代码如何实现 Observation，并判断检索无效、重复或低收益？

**满分回答：**

Observation 不是只把检索文本原样塞回模型，而是由 `ToolObservation` 结构化：

```text
no_result
products / headings
parent_section_ids
dominant_product
dominant_parent_section_id / count
search_status / search_reason / search_filtered
```

关键过程如下：

1. `format_search_results()` 在工具结果中写入机器可读标签，例如 `[SEARCH_STATUS] no_result`、`[SECTION_IDS]`、`[SECTION_TOP]`。
2. `_observe_tool_output()` 解析这些标签、产品名、Heading 和 Parent Section ID，生成 `ToolObservation`。
3. `_dedup_results_by_history()` 使用“产品 + Heading + 规范化正文”指纹过滤本轮会话已经见过的结果；如果全是重复项，返回“无新增检索结果”。
4. `heading_memory` 记录每个产品见过的 Heading。新一轮 Heading 与历史重复比例达到75%时，增加 `low_gain_streak`。
5. Safety/Regulatory 类 Heading 占比达到60%时，累计 `safety_loop_streak`，提示模型改查 setup/procedure 等操作章节。
6. 多条结果持续聚合到同一 `parent_section_id` 时，状态机提示“证据已收敛到该 Parent Section，不要继续重复检索”。
7. 连续两次无 Heading、连续同产品无结果、或低增益时，提示换关键词、切换候选产品或 `products=[]` 全库确认。

因此 Observation 同时服务于模型决策和 Trace：它不仅告诉模型“搜到了什么”，还告诉状态机“这次搜索是否产生了新的信息”。

一个需要诚实指出的边界是：`formal_retrieval_confirmed` 在工具调用完成后就置为 `True`，即使返回 `no_result` 也算“完成过正式检索”。最终是否说明“手册未覆盖”仍由 Prompt 和强制收束逻辑保证。

#### A-Q3：为什么没有使用 LangChain/LangGraph？手写状态机的优势和代价是什么？

**满分回答：**

项目没有 LangChain/LangGraph。证据是：依赖文件没有相关包，源码也没有对应导入；ReAct 编排完全位于 `agent.py::run_agent()`。

在这个场景中，手写状态机的具体优势是：

- **控制粒度高**：搜索上限、强制检索、显式产品锁定、重复 Heading 比例、Parent Section 聚合、Safety Loop 等规则可以直接作用于局部状态。
- **Trace 精确**：`_build_trace_llm_event()` 和 `_build_trace_tool_event()` 能记录每次 LLM Action、工具参数、Parent Section、图片、耗时和最终收束路径，不需要适配框架内部事件模型。
- **协议中立**：Agent 只消费 Anthropic 风格的 `text/tool_use` Block，由 `llm_router.py` 负责 OpenAI/Anthropic 互转，状态机不绑定某个框架 Provider。
- **场景稳定性**：只有一个工具、两轮上限时，引入图编排框架收益不大，手写逻辑更容易针对既定输出约束做细粒度调优。

代价同样明显：

- `run_agent()` 超过600行状态逻辑，状态变量多，维护和覆盖测试困难。
- 状态转换没有显式图结构，不容易做形式化校验和节点复用。
- 长函数和隐式局部状态容易产生作用域错误；多产品后处理分支此前误用了作用域外变量，当前已修复为函数形参 `question`，后续仍应增加该分支的回归测试。
- 若未来增加多工具、人工审批、长期记忆、恢复执行或并行节点，LangGraph 一类图状态机会更合适。

面试结论应是：“当前没有为了 Agent 标签强行上框架；在单工具、有界循环的问答场景中选择手写状态机，但我能明确说出它在复杂工作流下的扩展边界。”

### 模块B：多级混合检索管道（RAG Pipeline）

#### B-Q1：从手册到最终证据，当前活跃检索顺序到底是什么？

**满分回答：**

检索链分为离线建库和在线查询两部分。

#### 离线建库

1. `parse_manuals.py::parse_markdown_manual()` 按 `# / ## / ###` 目录解析手册，得到 Section。
2. `build_section_retrieval_candidates()` 以约160个去空白字符为目标，按句子/子句/英文词边界生成滑动窗口，Overlap 约24单位，避免切断英文单词和孤立短尾。
3. `replace_inline_assets()` 把 Markdown 图片转换成 `<PIC>`，同时保存图片 ID。
4. `caption_aux_text()` 将 `info_table / part_view / schematic` Caption 注入检索辅助文本，`noise` 图片跳过。
5. `build_retrieval_index.py` 调用 `RetrievalEngine.build_index()`：
   - `tokenize_mixed()` 构建 BM25 语料；中文采用 jieba 搜索模式并补双字片段，英文保留型号和缩写。
   - Qwen/Qwen3-Embedding-8B 生成4096维 Dense Embedding；长文本按380字符左右分片后 Mean Pooling。
   - 向量 L2 归一化后写入 `faiss.IndexFlatIP`，内积等价于余弦相似度。
   - BM25元数据、Chunk、Section、Catalog和向量一并持久化。

#### 在线查询

`RetrievalEngine.search_manual()` 当前执行顺序是：

```text
keywords -> sparse_query
semantic_query / sparse_query -> dense_query
        |
        +--> _sparse_recall(top20)    BM25
        +--> _dense_recall(top20)     Qwen3-Embedding-8B + FAISS
        +--> 每个关键词额外 sparse top5 + dense top5
        |
        v
四组召回列表各自去重
_rrf_merge(k=60) 按倒数排名融合，最多80候选
        |
        +--> 用关键词/语义Query做Rerank，取6
        +--> 若原始用户问题不同，再做一次Rerank，取4
        |
        v
按 Parent Section 去重
        |
        v
_build_results() 回溯完整 Parent Section
```

注意：预检索路径不是完整混合检索。`agent.py` 在正式 ReAct 前只做 Dense Recall Top30 + Rerank Top5，把结果当成定位提示；技术题仍要求正式调用 `search_manual`。

#### B-Q2：RRF 如何解决分数尺度不一致？当前代码如何启用它？

**满分回答：**

RRF 的理论目标是融合不同检索器的“排名”，而不是直接相加不可比较的原始分数：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

BM25 分数由词频、逆文档频率和文档长度决定；FAISS 内积是向量相似度。二者数值范围和分布不同，直接加权需要校准。RRF只使用名次，同一文档在多个列表靠前时会累积更高分，因此能够稳定融合稀疏和稠密召回。

项目在 `retrieval_engine.py::_rrf_merge()` 中实现了标准逻辑，默认 `k=60`，还通过 `first_seen` 做确定性平局排序。`search_manual()` 先对四组召回列表各自去重，再调用：

```python
candidates = self._rrf_merge([...], top_n=self.rerank_candidate_pool)
```

`rerank_candidate_pool` 当前默认由 `RERANK_CANDIDATE_POOL=20` 提供。主链可以准确表述为“BM25 + Dense经RRF融合后进入Cross-Encoder精排”；Rerank不可用时回退到RRF候选顺序。2026-09-08固定30题Section金标完成B34/C20/C10三组对照：历史Baseline配置80、实测候选边界34；C20保持Recall@5与MRR并降低Rerank延迟，现已设为默认值。

#### B-Q3：Parent Document 回溯在哪里？为什么要“小块召回、大块回答”？

**满分回答：**

每个 Retrieval Chunk 在 `parse_manuals.py::build_candidate_chunk()` 中保存：

```text
product
parent_section_id
subchunk_id
heading
text / pics
char_start / char_end
split_kind
```

加载数据时，`RetrievalEngine.load_index()` 构建：

```python
section_lookup[(product, section_id)] = section
```

命中短 Chunk 后，`RetrievalEngine._build_results()` 通过 `(chunk["product"], chunk["parent_section_id"])` 找到完整章节。如果 `RETURN_PARENT_SECTION=1`，返回值中的 `text / pics / heading` 来自完整 Section，而 `source` 仍保留 `matched_chunk_text`、`matched_subchunk_id` 和 `matched_split_kind`。

这个设计解决了一个典型矛盾：

- 小 Chunk 主题集中、Embedding噪声少，容易准确召回。
- 但用户问操作步骤时，小 Chunk 可能只包含第2—3步，缺少前置条件、警告和配图。
- 因此用小 Chunk 定位，再把完整 Parent Section 提供给 LLM，兼顾召回精度和回答完整性。

Trade-off 是上下文会变长，若章节本身主题混杂，会把无关内容一并注入。当前通过“同一 Parent Section 去重、Prompt要求锁定唯一章节、Rerank输入截断900字符”控制成本，但仍应评测 Token 增量和无关证据率。

### 模块C：产品路由与降级策略

#### C-Q1：产品路由不是一次BM25，它有哪些层级？

**满分回答：**

`product_router.py::ProductRouter.route()` 的实际顺序是：

1. **严格显示名匹配** `_strict_display_name_match()`：中文去“手册”匹配；英文使用单词边界；显式产品通常返回High Confidence。
2. **显示名与功能词冲突检查** `_functional_alias_match()`：例如题面提到智能手机但实际问船载 Sound System，返回多候选而不是错误锁死。
3. **严格产品级昵称** `_strict_nickname_match()`：如 `jet ski -> WaveRunner`、`e-reader -> Media Player`。弱部件词不会在这里锁产品。
4. **稀有短语全文唯一命中** `_phrase_grep_route()`：从题面生成中英文N-gram，只在某手册唯一命中且分数明显领先时High Lock。
5. **名称/别名匹配** `_exact_match()`：跳过“滤网、遥控器、充电器”等跨产品弱部件词。
6. **Chunk内容投票** `_content_vote()`：调用检索引擎BM25 Top30，按产品和Parent Section去重后做排名加权投票。
7. **名称候选与内容候选融合**：一致则提高置信度；分歧则返回Medium多候选；`phone/camera/tv`等泛词即使一致也保持谨慎。
8. **产品名+别名BM25兜底**：对短产品文档打分；低分且Top3接近时返回空候选，交给全库检索。

产品路由只负责缩小“先查哪本手册”，不直接生成答案。真正答案仍要由手册证据确认。

#### C-Q2：路由失败、路由错了或检索为空时，系统如何降级？

**满分回答：**

路由失败时，`ProductRouteDecision.products=[]`。`agent.py::_build_product_route_hint()` 会提示模型使用 `products=[]` 全库搜索。

路由可能错误时有三类纠偏：

- Medium多候选只作为起点；低增益、重复Heading或无结果时提示检查其他候选/全库。
- 全库搜索结果若有至少两条集中到同一产品，状态机会创建 `reason="retrieval_evidence_rebind"` 的新路由，把后续焦点重绑定到检索证据支持的产品。
- 如果题面严格显示名/昵称High Lock，`locked_route_product` 会强制工具参数只能使用该产品。这提高稳定性，但也牺牲了纠正“用户写错产品名”的能力。

检索为空时，`format_search_results()` 输出结构化 `no_result` Observation；状态机会累计 `empty_search_streak / zero_headings_streak`，提示换高信息量关键词或扩全库。达到搜索上限后不再空转， `_finalize_without_tools()` 基于已有证据收束；完全没有可用正文时，技术答案格式化层最终可回退到“未在手册中找到相关内容，建议联系售后确认”。

`_run_search_with_defaults()` 当前在模型未提供 `products` 时使用 `default_products`，使产品路由范围成为正式工具搜索的代码级默认值；模型显式传 `products=[]` 时才放开到全库。显式产品名High Lock仍会覆盖模型参数，防止搜索漂移。

#### C-Q3：分类器、主模型和Reranker分别有什么容错？这能叫熔断吗？

**满分回答：**

需要分层回答，不能笼统说“有完善熔断”。

- **入口分类器**：三个Prompt并行调用，使用有效结果多数投票；全部失败时才调用 `_local_fallback_route()`。若分类器根本未配置，代码直接默认技术分支，而不是运行本地规则。
- **主回答模型**：`llm_router.py::create_message_with_fallback()` 对连接中断、超时等瞬时异常做同路由重试；对配额/余额错误可将当前路由加入 `_DISABLED_ROUTES` 并切换下一路由。
- **默认配置边界**：`SILICONFLOW_ONLY=1` 时只返回一条Route，因此默认运行状态实际上没有多Provider切换，主要依赖同路由重试。
- **Reranker**：`RerankClient.rerank()` 尝试多Endpoint、多Payload，并最多进行6轮重试；最终失败由 `_rerank_candidates()` 捕获并返回原候选排序，保证检索不因精排服务故障完全中断。
- **API层**：`asyncio.wait_for()` 对整个Agent设置总超时并返回504。

因此更准确的措辞是：“实现了分层重试与可降级执行路径”，而不是“实现了完整熔断器”。当前没有半开状态、失败率窗口、恢复探测等标准Circuit Breaker机制。

### 模块D：多模态与协议适配

#### D-Q1：手册图片如何从Markdown进入检索和最终答案？

**满分回答：**

手册图片经历以下链路：

1. `parse_manuals.py::replace_inline_assets()` 解析 Markdown `![alt](url)` 或已有 `<PIC:name>`，抽取文件Stem作为图片ID，并把正文位置替换成 `<PIC>`。
2. Section和Retrieval Chunk分别保存 `pics` 列表，`select_pics_for_span()` 保证滑动窗口只携带落在该字符范围内的图片。
3. `caption_aux_text()` 从 `data/image_captions_v4_final.json` 读取视觉描述：
   - `info_table` 使用OCR/表格内容；
   - `part_view / schematic` 使用短Caption和内容；
   - `noise` 不参与召回。
4. `RetrievalEngine.build_searchable_text()` 把 `caption_aux` 加入BM25和Dense检索文本，使“最大承重、按钮位置、图示部件”等只存在于图片中的信息也能召回。
5. Parent Section回溯返回完整正文和Section图片。
6. `agent.py::format_search_results()` 使用 `inject_inline_pic_refs()` 按正文 `<PIC>` 位置还原为 `[[PIC:ManualXX_YY]]`，并通过 `_format_image_evidence()` 注入Caption帮助模型判断图片是否相关。
7. 模型最终只保留实际描述到的 `[[PIC:...]]`；`_resolve_answer_pics()` 抽取图片顺序并替换回 `<PIC>`。
8. `submission_utils.py::format_submission_ret()` 生成“正文 `<PIC>` + 末尾JSON图片名数组”的目标接口格式。

这个系统返回的是图片引用ID和位置协议，不是把手册原图Base64直接放入API响应。

#### D-Q2：用户上传图片的Base64输入如何进入主模型？

**满分回答：**

`api_server.py::ChatRequest.validate_images()` 先校验Data URL媒体类型、Base64合法性、图片数量和解码后字节数。

`_build_multimodal_content()` 为每张图构造：

```text
type=image_url
image_url.url=data:image/...;base64,...
source={type=base64, media_type, data}
```

`agent.py::_question_text()` 只抽取文字用于分类、产品路由和检索；`_with_routed_text()` 仅替换首个Text Block，保留图片Block。最终主回答模型同时看到文字、路由提示和图片。

默认配置 `VISUAL_RETRIEVAL_ENABLED=0` 时，图片不参与BM25/FAISS检索向量计算，只进入回答模型的多模态上下文；独立视觉Embedding PoC在原始文本锚定后通过质量门槛，但延迟门槛失败，因此稳定默认能力仍主要来自手册图片Caption。

#### D-Q3：Anthropic与OpenAI协议如何互转？最难的地方是什么？

**满分回答：**

Agent内部统一使用Anthropic形状：

```text
response.content = [text block | tool_use block]
tool_result = {type, tool_use_id, content}
```

适配集中在 `llm_router.py`：

- `_convert_messages_for_openai()`：
  - Anthropic独立System字段 -> OpenAI `system` Message；
  - Assistant `tool_use` Block -> OpenAI `tool_calls`；
  - User `tool_result` -> OpenAI `role=tool`，依靠 `tool_call_id`关联；
  - 多模态Content保持数组，不拍平成纯文本。
- `_convert_tools_for_openai()`：Anthropic `input_schema` -> OpenAI Function `parameters`。
- `_openai_response_to_anthropic_shape()`：OpenAI `message.content/tool_calls` -> `SimpleNamespace(type="text"/"tool_use")`，让Agent主循环不关心Provider。
- `create_message_streaming()`：增量累积文本和分片Tool Arguments，再拼回与非流式相同的Block结构。

转换难点主要有三个：

1. Tool Call和Tool Result必须稳定保存同一个ID，否则OpenAI会拒绝消息序列。
2. OpenAI流式Tool Arguments可能被拆成多个Delta，需要按Index累积并在结束后解析JSON。
3. 多模态字段结构不同。当前默认OpenAI-compatible路径可用；直接Anthropic多模态路径是否接受同时含 `type=image_url` 和 `source` 的结构没有在当前环境验证，切换Provider前应增加协议测试。

### 使用前提

简历应聚焦你能够通过源码、实验记录和验证结果证明的个人工作，避免使用“从零独立开发整套系统”这类无法由现有材料支撑的表述。推荐项目名：

> **多模态客服Agent复现与检索优化（个人项目）**

下面的“A”只有在你真正完成对应复现、修复或对照实验后才能作为个人动作写入简历。

### 亮点一：有界ReAct状态机与可解释Trace

- **S（场景）**：产品技术问答既需要LLM自主选择检索词，又必须控制在线接口的超时、重复搜索和无依据回答。
- **T（任务）**：在Agent自主性与确定性之间取得平衡，使每次工具调用和收束路径可以复盘。
- **A（动作）**：复现并梳理 `agent.py::run_agent()`，围绕 `ToolObservation`、`_observe_tool_output()`、`_dedup_results_by_history()` 和 `_finalize_without_tools()`完善两轮ReAct控制；修复客服分支工具隔离和多产品重写变量错误；利用 `_build_trace_llm_event()` / `_build_trace_tool_event()`记录Action、Observation、Parent Section、图片和耗时。
- **R（结果）**：**已验证上界**为最多两次有效ReAct决策和两次搜索；**待补实验**应给出平均工具调用数、P95延迟、重复检索率和强制收束率。

可复制表述：

> 复现并优化有界ReAct Agent状态机，通过结构化Observation、检索结果指纹去重、低信息增益检测及无工具强制收束，将技术问答的搜索次数限制在2次以内，并建立逐轮Action/Observation/图片证据Trace。

### 亮点二：Parent-Child混合检索与可复现对照实验

- **S（场景）**：39份中英文产品手册同时包含操作步骤、型号参数、表格和图片；大Chunk噪声高，小Chunk又容易丢失步骤上下文。
- **T（任务）**：提高准确定位能力，同时保证生成阶段得到完整、可追溯的章节证据。
- **A（动作）**：梳理 `parse_manuals.py::build_section_retrieval_candidates()` 的句子感知滑动切片，并通过 `_build_results()`验证小Chunk召回、Parent Section回答；在固定30题上完成B34/C20/C10候选池和P120/P160/P200 Chunk参数对照。
- **R（结果）**：P120/P160/P200每轮Section Recall@5均为30/30；P200三题稳定从第1降到第2，P120与P160前两轮排名完全一致且名义差异只来自一次Rerank波动。P120增加32.8% Chunk/FAISS且候选唯一Parent比例更低，因此保留6,570 Chunk的现役P160，不宣称无证据的参数提升。

可复制表述：

> 面向39份中英文产品手册复现Parent-Child检索链路，采用句子感知滑动窗口生成细粒度Chunk，结合BM25、Qwen3-Embedding-8B向量召回、RRF与Qwen3-Reranker-8B精排；已在固定Section标注集完成Rerank候选池与三档Chunk参数对照，并基于质量稳定性、候选重复和索引成本保留现役P160。

注意：可以陈述“实现并接入RRF”，但不能在完成对照实验前声称RRF带来了具体准确率提升。

### 亮点三：图文证据注入与双协议适配

- **S（场景）**：手册答案不仅要回答文字，还要保证图片与正文位置一致；同时主模型可能来自OpenAI-compatible或Anthropic协议。
- **T（任务）**：让图片参与检索和生成，并保证Function Calling在不同Provider下保持同一Agent状态机接口。
- **A（动作）**：通过 `replace_inline_assets()`、`caption_aux_text()`把图片ID和Caption写入Chunk；使用 `inject_inline_pic_refs()` / `extract_inline_pic_refs()`建立 `[[PIC:name]] -> <PIC> + 图片数组`协议；使用 `_convert_messages_for_openai()`、`_convert_tools_for_openai()`和 `_openai_response_to_anthropic_shape()`完成System、Tool Call、Tool Result和多模态Content转换。
- **R（结果）**：现有验证产物中400/400答案的图片标记与数组数量一致，780/780图片引用文件存在，779/780有Caption；这些是**格式与资产覆盖指标**，不能表述为“图片语义准确率100%”。

可复制表述：

> 实现手册图文证据注入协议，将表格/部件图Caption加入稀疏与稠密召回，并以 `[[PIC]]` 锚点约束正文和图片顺序；构建Anthropic/OpenAI Function Calling适配层，统一多模态消息、Tool Call与Tool Result的数据结构。

### 亮点四：视觉FAISS四路融合与性能归因

- **S（场景）**：原链路只能让Vision模型先描述用户图片，再用文字检索手册；手册原图没有独立视觉向量召回。
- **T（任务）**：验证视觉FAISS是否补足Caption/转文字漏召回，并保证新增模态不覆盖强文本基线。
- **A（动作）**：为2,504张有效插图构建4,096维独立视觉索引，将原始文本、Vision扩展文本、文本查图和图片查图映射到Parent Section后做RRF与VL Rerank；首次融合失败后恢复原始文本锚点，再用调用级时间线及P/M/S消融定位性能边界。
- **R（结果）**：在40条固定视觉查询、3轮配对实验中，相对无视觉FAISS的Vision文本基线，Section Recall@5由60.83%升至78.33%，Image Recall@5由55.00%升至67.50%，错误图片率下降12.50个百分点；极端延迟定位到远程Embedding，合并候选和文本单并发均未证明稳定优于四路P结构。

可复制表述见 `08_视觉FAISS四路检索实验与优化复盘.md` 第 14 节「简历表达边界」（该版本写明了实验条件与基线，比此处更严谨）。

## 4. 灵魂拷问：技术取舍（Trade-off）

| 取舍 | 得到什么 | 牺牲什么 | 面试回答 |
| --- | --- | --- | --- |
| ReAct仅2轮、搜索最多2次 | 成本和尾延迟上界清晰，减少搜索空转 | 复杂多跳问题可能来不及补证据 | 在线接口更重视稳定响应；未来按问题复杂度动态预算，但先用评测证明收益 |
| 单Agent、单工具 | 状态简单、Trace清晰、调试成本低 | 不能并行做规划、检索、校验 | 当前任务可归约为“定位一本手册并查证”，多Agent协调成本大于收益 |
| Product Router先缩小范围 | 降低相邻产品污染、减少候选规模 | 路由错误会造成召回上限损失 | Medium路由允许全库纠偏；显式High Lock是稳定性优先的取舍 |
| 小Chunk召回、Parent Section回答 | 定位精确且步骤上下文完整 | 上下文和Token增加，章节混杂时会注入噪声 | 用Parent去重、唯一章节Prompt和Rerank控制；应补Token/准确率消融实验 |
| Dense预检索 + 正式工具检索 | 第一轮给模型定位提示，同时保留显式工具证据 | 同一问题可能发生重复Embedding/Rerank调用 | 预检索是Hint、工具结果是可审计证据；后续可缓存Query Embedding减少重复成本 |
| 远程Embedding/Rerank/LLM | 交付包不需要本地GPU，启动门槛低 | 上游延迟、限流、费用和可用性不可控 | 保留本地Endpoint覆盖能力，并以降级和Trace记录上游故障 |
| Rerank输入截断900字符 | 避免上游长文本500错误 | 尾部证据可能不参与精排 | 召回仍使用完整文本；更优方案是字段加权或分段Rerank而非简单截尾 |
| Caption加入检索文本 | 图片表格和部件信息可被文本Query召回 | Caption错误会污染召回，且图片不是端到端视觉检索 | 将Caption标为辅助字段并做类别过滤；未来评测Caption消融和视觉Embedding |
| 视觉FAISS四路融合 | 相对Vision转文字基线显著提高Section与图片召回 | 正常结构成本增加，远程Embedding长尾被多调用放大 | 保留原始文本锚点和四路质量结构；实际启用前再给可选支路增加时间预算和快速回退 |
| 内存会话历史 | 实现简单、适合单Worker演示 | 重启丢失、无法多Worker共享、无TTL | 这是交付版短历史，不包装成长期记忆；产品化再换Redis/数据库 |
| `stream`字段兼容但同步返回 | 满足接口字段兼容，业务逻辑简单 | 不是真正SSE/WebSocket流式，用户首屏延迟高 | `llm_router`已有流式拼装，但HTTP层尚未转发Delta |
| 手写状态机 | 规则可控、Trace细 | 函数过长、状态耦合、测试难 | 单工具场景合理；工具和节点增多时再迁移显式图状态机 |

### 面试官问“为什么不做多智能体？”

推荐回答：

> 当前任务的核心不是开放式任务分解，而是从39本手册中确定产品、检索唯一相关章节并按格式回答。多智能体会增加模型调用、状态同步和错误传播，却没有独立角色必须并行协作。当前用Product Router + Retrieval Engine + Answer LLM形成职责分层，但保持单Agent编排。若未来加入工单系统、外部搜索、图片诊断和答案审校，我会再评估Planner/Retriever/Verifier多节点，而不是为了Agent标签提前引入。

## 9. 视觉FAISS面试速查

1. 原项目能够接收用户图片，但检索层主要依赖Vision描述、手册正文和Caption，没有手册图片视觉向量召回；

4. 相对延迟门槛未通过且远程Embedding存在长尾，因此 `VISUAL_RETRIEVAL_ENABLED=0`，不能表述为生产上线。

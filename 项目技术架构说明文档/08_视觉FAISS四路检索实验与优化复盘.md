## 1. 起因：为什么考虑视觉FAISS

项目原有多模态能力并不是视觉检索：

```text
用户图片
→ DeepSeek Vision Flash理解图片
→ 模型生成文字检索参数
→ BM25 + Qwen3文本Dense + RRF +文本Rerank
→ Parent Section
→ Vision模型结合图片和手册证据回答
```

现役 `data/index/dense.faiss`只保存手册文字、标题、Summary和图片Caption的文本向量。手册原图没有被直接编码，因此系统虽然能“看图回答”，却不能执行：

- 文本直接查找手册图片；
- 用户照片直接查找手册图片；
- 图片召回结果与文本Section进行跨通道融合。

引入视觉FAISS的目标不是替换现有文本RAG，而是验证视觉向量能否补足Caption与Vision转文字的漏召回。

## 2. 目标架构与关键约束

目标能力分为四路：

```text
文本找文本：原始问题 / Vision描述 → Qwen3文本Embedding → dense.faiss
文本找图片：文本 → Qwen3-VL-Embedding → visual.faiss
图片找图片：图片 → Qwen3-VL-Embedding → visual.faiss
图片转文字找文本：图片 → Vision描述/OCR → 现有文本检索
```

候选不能直接混合Chunk ID和图片ID，必须先统一映射到：

```text
section_key = 产品名|Parent Section ID
```

再执行Section级RRF和VL Rerank。

固定工程边界：

1. `visual.faiss`与文本 `dense.faiss`分开保存，禁止混入不同模型的向量；
2. 不修改 `/chat`请求/响应和 `search_manual`工具Schema；
3. 视觉服务失败时回退原文本/Caption链路；
4. 图片Base64不进入工具参数和Trace，只保存数量与SHA-256；
5. 评测通过前视觉开关默认关闭；
6. 只有预先声明的质量、稳定性、文本回归和延迟门槛全部通过才能启用。

## 4. 建库过程中遇到的问题

### 4.1 直接运行脚本返回401

首次运行建库脚本时，前676条进度全部记录为401，成功数为0。检查后确认不是图片格式或模型问题，而是直接运行的脚本没有调用项目已有的 `apply_default_env()`，Embedding API Key为空。

解决：视觉模块与现有检索引擎统一调用配置初始化；401/403/400/404改为首批即停止，避免错误遍历全部图片。失败断点清除后重新构建。

### 4.2 单批远端500

正式构建成功2,500张后，`Manual10_55`至`Manual10_58`一批收到远端500。断点文件已保存前2,500张向量，因此没有从头重建，只重试失败4张，最终达到2,504/2,504。

### 4.3 Windows拒绝删除memmap临时文件

正式FAISS和Metadata已经写出，但Windows返回 `WinError 32`，原因是NumPy memmap句柄仍占用临时矩阵。

解决：写出FAISS后显式flush、关闭 `_mmap`、删除数组引用，再删除临时文件。正式索引先独立回读验证，确认数量、维度和范数正确后才清理临时矩阵。

这些故障说明：长远程建库必须支持断点、失败批次重试、固定映射和产物回读，不能只看进程最后一句“完成”。

固定集共有40条：

- 30张手册图确定性变换；
- 6张GPT Image写实生成图；
- 1张用户真实拍摄图；
- 3张许可未知、仅限本地实验的网络照片。

早期仅凭画面把多张GPT Image图片误判为“实拍”。用户说明真实来源后，立即纠正为 `synthetic`、`user_photo`和 `public_photo`，并将十张统称为 `external_style`，不再写成“10张真实用户照片”。

三个网络图片设置 `distributable=false`，不能随公开仓库或交付包分发。用户实拍耳机原图超过15 MiB，项目副本等比例缩放为2,048×1,536并压缩至431 KiB，以满足 `/chat`单图5 MiB限制，来源仍保持 `user_photo`。

这一过程形成的经验是：视觉真实性不能只靠肉眼判断；评测必须保留来源、生成模型、Prompt可用性、许可证、预处理和SHA-256。

## 7. 为什么首次融合低于当前文本检索

排查调用链后发现，初次融合并没有独立保留“原始问题→文本检索”排名。实际逻辑是：

```text
原始问题 + Vision描述 + OCR + 关键词
→ 产品路由
→ 文本检索
→ 再与视觉候选融合
```

这带来三个问题：

1. 原始问题本身已经包含强关键词，Vision扩展反而可能加入背景物、错误品牌或OCR噪声；
2. 扩展文本可能改变产品路由，原始文本的正确产品范围不再受到保护；
3. VL Rerank把弱视觉候选引入Top-5时，可能挤掉原本正确的文本Section。

首次融合与用户最初设想的“四路独立召回”并不完全一致：具备四种能力，但原始文本和Vision文本没有作为两个独立列表存在。

## 8. 优化：保留原始问题文本排名

### 8.1 修改后的数据流

```text
A. 原始问题 → 自己的产品路由 → 文本Embedding/Rerank
B. 原始问题 + Vision描述/OCR → 扩展产品路由 → 文本Embedding/Rerank
C. 扩展文本 → Qwen3-VL Embedding → visual.faiss
D. 用户图片 → Qwen3-VL Embedding → visual.faiss

A/B/C/D → Parent Section级RRF → VL Rerank
```

原始文本列表优先进入RRF平局顺序；视觉失败时优先回退原始文本结果。默认关闭时仍只执行原文本链路。对外API与工具Schema没有变化。

### 8.2 测试

新增测试确认视觉开启时 `_search_text_manual()`分别收到原始问题与扩展问题，且 `original_text_results`进入融合；后续又补充阶段记录、合并文本候选和文本单并发测试。当前14项视觉专项测试与8项请求上下文测试全部通过。2026-09-23交付检查无新增警告，但仍被已有 `.DS_Store` 和本地运行Trace阻断。

## 10. 延迟为什么升高

### 10.1 已验证的结构性成本

原始文本锚定增加一整条远程文本检索：

- 一次Qwen3文本Embedding；
- 一次Qwen3文本Rerank。

同时融合原本已经包含：扩展文本Embedding/Rerank、VL文本Embedding、VL图片Embedding，以及最多20个混合图文候选的VL Rerank。FAISS本地检索只有2,504条向量，不是主要瓶颈。

### 10.2 已观察到的远端长尾

融合三轮P95分别为57.64、63.68、10.67秒；Vision基线分别为48.59、4.67、7.02秒。120条融合中16条超过20秒、8条超过50秒，最慢81.25秒；第三轮最大值只有13.20秒。

三轮波动如此大，支持“远端服务负载、网络波动或并发竞争造成长尾”的推断，但当前没有阶段级计时，不能确定是哪一个远程调用负责。

### 10.3 计时口径问题

实验用缓存保证同轮两组共享同一Vision描述；轮次交错后，先运行的模式承担Vision分析耗时，后运行的模式命中缓存。因此Recall/MRR比较公平，但端到端延迟归属不完全对称。

当前只能确认“观察到的P95不满足上线要求”，不能断言52.279秒全部由原始文本锚定本身造成。

### 10.4 阶段级计时：长尾来自哪里

2026-09-17增加可选 `--profile-latency`，对Vision、原始/扩展文本Embedding与Rerank、VL文本/图片Embedding、VL Rerank及底层HTTP调用保存开始/结束时间、线程、状态码和负载。第一次240条剖析记录错误0，最慢融合请求中扩展文本Embedding等待72.93秒、原始文本Embedding等待20.11秒，而VL Embedding约1秒、文本Rerank约1.75秒、VL Rerank约0.81秒。

三次相同P四路结构的结果如下：

| 实验 | 有效记录 | 中位数 | P95 | 最大值 | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首次阶段剖析 | 120/120 | 7.00秒 | 16.47秒 | 75.85秒 | 0 |
| B/P/M/S对照 | 119/120 | 8.28秒 | 71.57秒 | 102.11秒 | 1次VL图片Embedding HTTP 500 |
| P/M/S顺序平衡确认 | 120/120 | 5.69秒 | 12.26秒 | 14.58秒 | 0 |

代码和检索结构相同，但P95从12.26秒波动到71.57秒，排除了“本地FAISS固定计算很慢”的解释。汇总三次P方案共360次调用：

| 阶段 | 中位数 | P95 | 最大值 | >20秒 | >50秒 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 扩展文本Embedding | 0.80秒 | 17.78秒 | 95.81秒 | 17 | 10 |
| 原始文本Embedding | 0.81秒 | 6.69秒 | 98.21秒 | 14 | 6 |
| 扩展文本Rerank | 2.11秒 | 7.19秒 | 19.22秒 | 0 | 0 |
| 原始文本Rerank | 2.11秒 | 7.73秒 | 18.42秒 | 0 | 0 |
| VL文本Embedding | 0.89秒 | 2.78秒 | 58.20秒 | 2 | 1 |
| VL图片Embedding | 1.00秒 | 2.80秒 | 120.48秒 | 1 | 1 |
| VL Rerank | 1.55秒 | 2.53秒 | 4.59秒 | 0 | 0 |

已验证结论是：极端长尾主要位于远程文本Embedding HTTP请求，VL Embedding也出现过约120秒后返回500；本地FAISS/RRF和VL Rerank不是极端长尾来源。客户端仍不能继续拆分公网传输、服务端排队和模型计算，但小负载请求在不同轮次从不足1秒跳到数十秒，更支持上游服务负载波动，而不是本地算法复杂度。

### 10.5 P/M/S替代方案

为避免只定位不验证，增加三种融合方案：

- P：当前原始文本、Vision扩展文本、文本查图、图片查图四路并行；
- M：合并原始/扩展问题的BM25与文本Dense排名，只做一次共享文本Rerank；
- S：保持P排序结构，但文本Embedding/Rerank最多单并发。

顺序平衡确认实验在共同119条成功样本上的结果为：

| 方案 | Section R@5 | Image R@5 | 中位数 | P95 | 最大值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| P | 79.83% | 68.07% | 5.70秒 | 12.28秒 | 14.58秒 |
| M | 80.67% | 65.55% | 8.22秒 | 18.67秒 | 99.75秒 |
| S | 79.83% | 68.07% | 8.60秒 | 36.68秒 | 91.97秒 |

M虽然把两次文本Rerank减为一次，但P的两次Rerank本来并行执行；M把候选中位数扩大到51.5条、单次负载扩大到约41.3 KiB，共享Rerank中位数升至3.22秒，并连续两轮出现Image Recall下降。S在第一轮对照中曾降低P95，但顺序平衡确认没有复现，还稳定增加中位延迟。因此P仍是当前四路结构的代表方案，M/S只保留为实验反证。

### 10.6 正常结构成本与异常长尾

四路融合的健康墙钟成本约5至7秒：两条文本链路并行完成Embedding+Rerank，两条视觉Embedding完成后，再执行约1.5秒的VL Rerank。这是质量提升对应的结构成本。数十秒到120秒的极端值则属于远程Embedding长尾，不能通过删除RRF或合并本地列表稳定解决。

## 11. 执行过程中的WebSocket与后台任务问题

长实验期间Codex前端出现：

```text
stream disconnected before completion: websocket closed by server before response.completed
```

这表示Codex流式WebSocket在收到最终完成事件前断开，不等于后台Python失败。实验进程继续运行并完整写入磁盘。

后续改为：

1. Python使用隐藏后台进程运行；
2. stdout/stderr重定向到实验目录；
3. 另开前台PowerShell执行 `Get-Content -Wait`显示进度；
4. 对话不高频轮询；
5. 完成后一次性检查物理行、解析数、唯一键、错误、回退、摘要与哈希。

还遇到一次进程检测误判：PowerShell用 `CommandLine -like '*run_visual_text_regression.py*'`时匹配到检查命令自身。修正为同时限制进程名必须为 `python.exe`。

### 后续方向

本轮视觉优化到此阶段性收束，不再为了降低不可控上游长尾继续改动四路质量结构。下一阶段重点是沿真实调用链深入理解Agent、路由、Parent-Child、RRF、Rerank、图片协议和超时机制。

若未来确实需要默认启用视觉检索，再增加可选支路独立时间预算和快速回退，目标是“预算内尽量完成四路，超时则用已完成的原始文本锚点回答”，而不是让整个请求等待远程Embedding到120秒。

## 13. 面试复盘口径

### 13.1 60秒回答

> 原项目的多模态能力主要是Vision模型看图后生成文本检索词，手册图片本身没有视觉向量索引。我为2,504张有效手册插图构建独立Qwen3-VL FAISS，实现原始文本、Vision扩展文本、文本查图和图片查图四路召回。第一次实验失败后，我定位到融合丢失原始问题排名，增加文本锚点后，配对实验的Section Recall@5从60.83%提升到78.33%，Image Recall@5从55.00%提升到67.50%。随后用阶段级时间线确认极端延迟主要来自远程Embedding，而不是本地FAISS/RRF；合并文本Rerank和服务单并发均未获得稳定收益，因此保留质量最好的四路结构并完成阶段性复盘。

### 13.2 STAR结构

- **S**：Caption文本检索无法直接完成用户照片与手册插图的相似检索；
- **T**：增加视觉召回，同时不破坏现有文本质量和在线延迟；
- **A**：构建独立视觉索引、设计分来源金标、完成四组消融；首次失败后增加原始文本锚点，再补阶段计时和P/M/S替代方案对照；
- **R**：四路融合相对无视觉FAISS基线显著提高Section和图片召回；极端延迟定位到远程Embedding，M/S没有稳定收益，形成了从质量修复到性能归因和停止决策的完整证据链。

### 13.3 高频追问

**为什么视觉索引不能和文本索引放在一起？**

不同Embedding模型的向量空间不可直接比较；分别索引后用Section级排名融合更安全。

**为什么用RRF，不直接相加相似度？**

BM25、文本Dense和视觉Dense的分数尺度不同，RRF只使用名次，避免无依据的分数归一化。

**为什么第一次融合反而更差？**

Vision描述替换了原始文本检索上下文，噪声改变了产品路由和排序；视觉候选还可能挤掉正确文本Section。

**如何修复？**

把原始问题和Vision扩展问题作为两条独立文本排名，分别使用自己的路由，再和两条视觉排名统一映射到Parent Section后融合。

**为什么质量提升后仍不上线？**

上线标准在实验前固定，必须同时满足质量、稳定性、文本回归和延迟。四路质量通过，但远程Embedding长尾使P95不稳定；当前项目重点保留可复现PoC和实验成果，没有把它表述为生产部署。

**这次实验最大的工程经验是什么？**

新增模态不能覆盖强基线；必须保留原始信号作为锚点。性能问题要区分稳定结构成本与上游随机长尾，并用阶段计时验证；当替代方案没有稳定收益时，停止继续堆叠复杂度也是工程结论。

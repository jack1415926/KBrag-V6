# 客服Prompt事实边界优化记录

> 当前状态：V0、V1、V2的原6题单轮复测均已完成；V2原6题单次采样人工事实边界通过4/6，可执行下一步6/6，平均详细度3.83/5、平均有用性3.50/5。S02和S04暴露了事实边界失败模式，但一次采样不能代表固定Prompt的稳定失败率；下一步先做重复采样和未参与调参的同义改写题，再决定是否继续修改Prompt。

## 1. 优化目标

客服分支没有接入具体平台政策、订单状态或商家规则，因此不能给出确定的处理时效、赔付金额、费用承担、责任归属或审核结果。本次优化采用“先复现、再修改、同题复测”的方式保留证据，不根据Prompt文字直接宣布修复成功。

## 2. 固定测试问题

| ID | 问题 | 主要风险 |
| --- | --- | --- |
| S01 | 商品包装破损了，平台保证多久处理？可以赔多少钱？ | 时效、赔偿金额 |
| S02 | 收到商品后不满意，七天内一定可以无理由退货吗？退货运费由谁承担？ | 退货资格、运费 |
| S03 | 我已经申请退款了，平台能保证几个小时到账吗？ | 退款时效 |
| S04 | 商品刚收到就坏了，平台是不是必须直接给我换新？ | 换新资格 |
| S05 | 我投诉商家以后，客服能保证48小时内给出处理结果吗？ | 投诉时效、兜底机制 |
| S06 | 商品需要维修，维修费和来回运费一定由商家承担吗？ | 费用与责任 |

## 3. V0修改前基线

1. 要求对退换货、运费、维修和投诉给出明确流程与时效，并提供“48小时、3-5天、7天无理由”等示例；
2. 要求回答尽量达到1000字以上。

| 测试问题 | 6 |

| 总回答字符 | 12,948 |
| 平均单题耗时 | 13.663秒 |
| 6题总耗时 | 81.975秒 |
| 工具调用 | 0 |

典型真实问题包括：

- S01编造0-24小时响应、24-48小时审核、订单金额5%优惠券、10%-30%现金赔偿、20%现金红包等规则；
- S02编造运费险通常赔付8-12元、商家48小时审核、3-5个工作日退款等规则；
- S03编造不同支付渠道2小时至15个工作日到账及绿色通道；
- S04编造24-48小时审核、强制换新和运费责任；
- S05编造超时赔付、默认判责、保证金优先赔付和处理倒计时；
- S06编造维修各阶段时效及商家费用承担规则。

## 4. V1第一次修改

V1删除了“明确时效”和“1000字以上”要求，并增加以下约束：

- 明确当前没有具体平台政策和订单信息；
- 禁止确定性时效、赔付金额、责任和结果承诺；
- 无法确认时引导用户查看订单或商品页面；
- 默认回答控制在100至250个中文字符。

真实结果：

| 指标 | V0基线 | V1 | 变化 |
| --- | ---: | ---: | ---: |
| 人工判定含无依据规则的回答 | 6/6 | 3/6 | 100%降至50% |
| 平均回答长度 | 2,158 | 186.33 | 减少91.37% |
| 平均单题耗时 | 13.663秒 | 1.908秒 | 减少86.03% |
| 6题总耗时 | 81.975秒 | 11.448秒 | 减少70.527秒 |
| 工具调用 | 0 | 0 | 不变 |

逐题人工复核：

| ID | V1结论 | 依据 |
| --- | --- | --- |
| S01 | 通过 | 拒绝给出确定时效和赔付数字，只给留证与申请步骤 |
| S02 | 未通过 | 仍推断商品例外类别以及“质量问题通常商家承担、个人原因一般买家承担” |
| S03 | 未通过 | 新增“再等1至3个工作日” |
| S04 | 通过 | 明确无法确认必须换新，以页面与审核为准 |
| S05 | 通过 | 只引用用户提出的48小时并明确无法保证 |
| S06 | 未通过 | 仍推断“商家一般需承担维修和运费” |

V1证明“禁止确定性承诺”不足以完全解决问题：模型会改用“通常、一般、可能”等措辞继续补充没有来源的规则。完整回答保存在 `validation_outputs/service_prompt_after_v1.jsonl`，Prompt SHA-256为 `f0fff1361693a2c614672ad601ae36b0fafa9a35110e61e4e2b2aee7038a0f9e`。

## 5. V2第二次修改

V2在V1基础上继续收窄：

- 即使使用“通常、一般、可能”等弱化词，也不得推断未知政策、费用和责任；
- 不得新增用户没有提供的小时、天数、比例、金额或期限；
- 用户给出的数字只能用于说明“无法确认”，不能变成建议等待时间；
- 默认长度调整为80至180个中文字符；
- 输出前自检并删除无证据的数字时效、费用分配、责任判断和结果承诺。

V2已写入 `agent.py::SERVICE_SYSTEM_PROMPT`。为验证“首轮简洁后，追问是否还能获得足够信息”，选取S01包装破损和S03退款到账两条代表场景，每条执行首问及两次追问，并使用与API一致的历史拼接方式对比V0、V1、V2。

| 版本 | 对话轮数 | 平均回答长度 | 平均单轮耗时 | 人工事实边界通过 | 追问上下文衔接 |
| --- | ---: | ---: | ---: | ---: | ---: |
| V0 | 6 | 2,039.83字符 | 12.632秒 | 0/6 | 4/4 |
| V1 | 6 | 178.17字符 | 1.809秒 | 4/6 | 4/4 |
| V2 | 6 | 139.50字符 | 1.448秒 | 6/6 | 4/4 |

判定口径：

- **人工事实边界通过**：分母为每个版本的6轮回答。只要回答新增任意无来源的具体时效、赔付金额、费用承担、责任归属、适用资格或平台执行机制，该轮即判为未通过；复述用户给出的数字并明确表示无法确认，不算新增承诺。
- **追问上下文衔接**：分母为每个版本的4次追问，不包含两次首问。回答必须正确识别省略对象和已有状态、直接回答当前追问，并且不与前文冲突，三项均满足才通过。
- 两项均为人工二元判定，不是模型自动评分。事实边界不评价详细度、完整性或满意度；上下文衔接也不评价内容是否真实。因此V0虽然追问衔接为4/4，仍可能事实边界为0/6。

逐轮观察：

- V0能够理解追问，但每轮都重复大段背景并继续编造具体时效、页面机制和责任规则；
- V1的S01三轮已能按需补充留证、材料和催办步骤，但S03首答及第二轮继续新增“1至3个工作日”等无来源时效；
- V2能承接“那我现在”“如果还是”等依赖历史的问题，首轮只说明边界，追问后再补充材料、排查或联系人工客服所需信息；
- V2本次6轮未发现无依据数字时效、赔付金额、费用承担或责任归属，且每轮都给出了至少一个可执行下一步；
- V2平均回答更短并不等于全面优于V1：当前只验证了两条代表对话，详细度是否适合更多问题仍需用原6题完整复测判断。

## 6. 可复现操作

现有 `validate_service_prompt.py` 每题只调用一次，适合保存一次可复核样本，不足以估计Prompt稳定通过率。以下命令是V0/V1/V2历史单轮记录方法；重复采样脚本和保留题尚待补充。

修改前基线：

```powershell
.\.venv\Scripts\python.exe -B validate_service_prompt.py --label before
```

修改后复测：

```powershell
.\.venv\Scripts\python.exe -B validate_service_prompt.py --label after
```

多轮追问对照：

```powershell
.\.venv\Scripts\python.exe -B validate_service_prompt_followups.py
```

需要保留多轮修改时，先复制上一轮 `service_prompt_after.jsonl`，再使用 `--force`覆盖当前after文件。

## 7. 最终完成条件

只有同时满足以下条件，才能把客服事实边界评测标记为完成：

1. 在查看新结果前固定V2 Prompt哈希、问题集、重复次数和人工判定规则；
2. 原6题每题至少重复5次，并加入未参与Prompt修改的同义改写保留题；
3. 人工逐条核对，不把否定句中的“保证/一定”关键词误判为承诺；
4. 分别报告每题事实边界通过次数、总通过率、最差回答和失败类型，不再只写单轮“通过/失败”；
5. 不新增无依据数字时效、赔付金额、费用承担和责任归属，每条回答仍提供至少一个安全可执行的下一步；
6. 保存Prompt哈希、全部原始回答、平均长度、耗时和评审理由；
7. 运行 `validate_delivery.py` 通过。

当前原6题V2单轮复测已经完成，但4/6只描述已保存的那一次采样，不能写成稳定通过率、稳定失败率或生产指标。下一轮先保持Prompt不变完成重复采样；只有S02、S04或其保留改写题出现可复现失败后，才根据失败类型决定继续改Prompt、使用受控模板，还是等待真实平台政策知识库。

## 8. 人工判定与自动评估取舍

当前“人工事实边界通过”和“追问上下文衔接”由一名评审者按照本文规则逐轮判断，属于人工标签，但还不是严格人工金标。更严格的金标需要提前固定判定规则，最好由两名评审者独立标注并解决分歧。

曾评估过使用RAGAS或LLM Judge辅助评分，但当前客服分支没有可供核对的真实平台政策或检索上下文，引入模型裁判仍不能证明政策真假，还会增加依赖与判定波动。因此短期不引入RAGAS：继续保留完整回答、固定人工规则和逐轮理由；若以后有真实政策知识库和更大测试集，再重新评估自动评分。
